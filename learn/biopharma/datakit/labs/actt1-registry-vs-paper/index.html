1. The question

Do the results posted on ClinicalTrials.gov for the ACTT-1 trial of remdesivir (NCT04280705) carry the same primary outcome and the same participant counts as the trial's final report in the New England Journal of Medicine?

A trial is reported twice, once in a journal and once in a public registry, by different routes and in different layouts. Reading the two side by side shows how a registry record is built (arms, participant flow, baseline, outcome measures, analyses, adverse events) and where its numbers sit in a paper.

From: Table 2, the two Overall columns (rows: median time to recovery, rate ratio, deaths by day 29); Table 1, row Male sex; Results text, sections Patients and Safety Outcomes[1]

2. Where this data lives in a company

Systems of record
Clinical trial management system, Electronic trial master file
Owner
The responsible party for the record. ClinicalTrials.gov defines it as the sponsor, the sponsor-investigator, or a principal investigator designated by the sponsor. This record names the sponsor (NIAID) as the responsible party.
Standards
None named by a source

ClinicalTrials.gov states that its data are provided by the organisations and institutions that sponsor and implement the studies. Results are entered as summary tables that follow the registry's own data element definitions (participant flow, baseline characteristics, outcome measures with statistical analyses, adverse events). The record holds no patient-level data. None of the standards in this kit's registry applies to the record.[2][3][4]

6. What goes wrong in practice

  • The arms are in a different order. The registry lists Placebo first and Remdesivir second in every results table. Table 2 of the paper prints Remdesivir first. Pick a group by its title, never by its position. Seen in this lab's data; the notebook shows it.
  • Group ids change from one module to the next. The same arm is FG001 in participant flow, BG001 in baseline, OG001 in outcome measures and EG001 in adverse events. Baseline also has a third group, Total. An id is only valid inside its own module, and inside one outcome measure. Seen in this lab's data; the notebook shows it.
  • Most numbers are stored as text. Outcome values and participant flow counts arrive as strings such as "15", "1.29" and "<0.001". The subgroup measures print "15.0" where the overall measure prints "15". Counts in the adverse events module are numbers. Check the type, convert on purpose, and keep the p-value as text. Seen in this lab's data; the notebook shows it.
  • Four measures are marked primary. The record has four outcome measures of type PRIMARY (time to recovery overall, by race, by ethnicity and by sex). Filtering on the type alone returns all four. Filter on the title as well. Seen in this lab's data; the notebook shows it.
  • The effect measure has a different name. The registry labels the analysis parameter "Cox Proportional Hazard" with the method "Log Rank". The paper calls the same number the rate ratio for recovery, and its Table 2 footnote says it comes from a stratified Cox model with a stratified log-rank test. A ratio above 1 favours remdesivir here because the event is recovery. [1]
  • The denominator depends on the table. Deaths are counted over everyone randomized (521 and 541). Serious adverse events are counted over the people who received treatment, as treated (516 and 532). The adverse events module says so in its description. Read the number at risk before you compute a percentage. Seen in this lab's data; the notebook shows it.
  • One quantity can be posted twice and differ. The outcome measure for serious adverse events posts 24 percent for remdesivir. The adverse events module of the same record gives 131 of 532, which is 24.6 percent. When two places disagree, go back to the counts. Seen in this lab's data; the notebook shows it.
  • The registry does not hold everything in the paper. Table 2 of the paper gives the number of recoveries and repeats each result by baseline ordinal score. The registry record has neither. It posts time to recovery by race, ethnicity and sex. Seen in this lab's data; the notebook shows it.
  • The record can change after you read it. Results were first posted on 2020-09-25 and the record was last updated on 2022-03-14. The registry reprocesses its data regularly and the version file changes each time. Note the last-update date and the processing date with every number you take from a record. Seen in this lab's data; the notebook shows it.

7. The same job on each platform

  • Open source executed here The lab's notebook reads the ClinicalTrials.gov API record for NCT04280705 as JSON, puts the primary outcome and participant counts into pandas tables, and compares them with the values copied from the journal report. This site's check runs it in a fresh Python process.[5]
  • Open source documented, not executed herepublisher-published DuckDB is a SQL database that runs inside the calling program, with no separate server, and reads JSON, CSV and Parquet files. A learner could save the registry record as a JSON file and select the outcome and participant counts with SQL instead of pandas. Not done here.[6]
  • Snowflake documented, not executed herevendor-published Snowflake is a self-managed service on public cloud infrastructure that cannot be installed and run locally. Its tables store structured and semi-structured data, such as JSON. A learner with an account could load the registry record into a table and query the outcome measures there. Not done here.[7]
  • AWS documented, not executed herevendor-published Amazon S3 is object storage, with management features to organise data and configure access. A learner with an account could keep the downloaded registry record and the article file as objects in a bucket, as the stored inputs for the comparison. Not done here.[8]
