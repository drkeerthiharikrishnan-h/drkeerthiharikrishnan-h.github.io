1. The question

How do you count people, people exposed to a drug, and diagnoses during exposure in an OMOP common data model database with standard SQL? The data are synthetic (simulated patients).

Observational studies in the OMOP common data model are written as SQL against a fixed set of tables and a shared vocabulary. The same query then runs on any database in the model. Counting persons, drug users at ingredient level and events during exposure are the first steps of most such studies, and each has a known trap.

From: Appendix E, section E.5 SQL and R, Exercises 9.1 to 9.3; section E.2, Exercise 5.1[1]

2. Where this data lives in a company

Systems of record
Warehouse or lakehouse, Electronic health records and claims
Owner
This dataset: OHDSI, which publishes it as a sample CDM dataset for testing, under Apache-2.0, in the OHDSI/EunomiaDatasets repository.
Standards
OMOP CDM

An OMOP database is a set of tables (PERSON, DRUG_EXPOSURE, CONDITION_OCCURRENCE, DRUG_ERA and others) plus the standardized vocabulary tables (CONCEPT, CONCEPT_ANCESTOR). Clinical rows point to concepts by id; the vocabulary gives names and hierarchies.[2][3]

6. What goes wrong in practice

  • Rows are not people. A person can have many drug exposures. Counting rows of DRUG_EXPOSURE counts prescriptions or dispensings; counting people needs COUNT(DISTINCT person_id). [1]
  • Drugs are recorded below the ingredient. To find everyone on celecoxib, the book joins DRUG_EXPOSURE through CONCEPT_ANCESTOR to the ingredient concept, so that every drug containing celecoxib is found. The alternative is DRUG_ERA, which the book describes as already rolled up to the ingredient level. [1]
  • Overlapping exposures double-count events. Two exposures to the same ingredient can overlap. A diagnosis inside both is counted twice if you join to DRUG_EXPOSURE. Drug eras do not overlap, so the book joins to DRUG_ERA. [1]
  • Join on the person as well as the dates. The query printed for Exercise 9.3 joins diagnoses to drug eras on dates only, so a diagnosis can be paired with another person's era. This lab reads "during exposure" as a statement about one person, so in its own reading (not the book's) a query that answers the exercise needs condition_occurrence.person_id = drug_era.person_id. This lab checks the query as printed against the book and shows the person-matched count beside it. [1]
  • The data version matters. The book's answers come from the Eunomia R package at v1.0.0. The GiBleed zip used here was added to a separate repository in 2022 and changed twice in 2023 (a cost table column name fix, then the removal of invalid vocabulary records). Record which file, and which commit, a count came from. [3][5]
  • Synthetic data answer no clinical question. The patients in GiBleed are simulated. Use the counts to learn the tables and the SQL, not to say anything about celecoxib or bleeding in real people. [3]
  • The printed answer is reproduced by the printed query, not by the question. The query printed for Exercise 9.3 returns 41 on this file, the number the book prints. All 41 of the pairs it finds join a diagnosis to another person's celecoxib era. With the person match the count is 0. In this file the 355 people who have both a celecoxib era and a bleeding diagnosis all have the diagnosis after the era ends. Seen in this lab's data; the notebook shows it.
  • A zip made on a Mac carries extra entries. GiBleed_5.3.zip holds a __MACOSX folder beside the 37 tables. Its entries are not tables. Filter them out before you load anything. Seen in this lab's data; the notebook shows it.

7. The same job on each platform

  • Open source executed here The lab's notebook loads the CSV tables of the synthetic Eunomia GiBleed database with pandas and writes them into SQLite with Python's built-in sqlite3 module. It reads the Book of OHDSI SQL for the exercises from the downloaded Suggested Answers page, runs it with sqlite3, and checks each count against the book's answers. This site's check runs it in a fresh Python process.[6]
  • Open source documented, not executed herepublisher-published The OMOP CDM site describes each released version of the model, its table and field conventions and the OHDSI standardised vocabularies. A learner would read the PERSON, DRUG_EXPOSURE and CONDITION_OCCURRENCE definitions there before writing the counting queries. Not done here.[7]
  • Databricks documented, not executed herevendor-published These Databricks notebooks ingest synthetic Synthea CSV records into a Delta bronze layer, define the OMOP 5.3.1 tables and vocabulary tables, and run an example ETL into OMOP. A learner with a workspace could adapt the lab's SQL counts to run against those tables. Not done here.[8]
  • AWS documented, not executed herevendor-published Amazon Athena is an interactive query service that runs standard SQL directly on data in Amazon S3. A learner with an account could store the Eunomia tables as files in a bucket and run the person and drug-exposure counts there. Not done here.[9]
