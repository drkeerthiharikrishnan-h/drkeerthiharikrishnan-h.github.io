Comparing two arms of a trial from its patient-level file

Open the public patient-level file of the International Stroke Trial, count deaths within 14 days by allocated treatment, and check the counts, percentages and differences against the numbers printed by the trial's authors. The deaths comparison and the final-diagnosis table reproduce; four descriptive counts in the data paper's text do not, and the notebook shows them.

1. The question

In the International Stroke Trial, did aspirin allocated at randomisation within 48 hours of a suspected acute ischaemic stroke reduce deaths in the first 14 days?

Comparing an outcome between the arms of a randomised trial is the basic analysis of clinical development. Here the whole chain is public, from one row per patient to the two percentages in the report, so each step can be run and checked. The trial is factorial, so the same file answers a second question, about heparin.

From: PubMed record PMID 9174558, abstract, section RESULTS: the sentence on deaths within 14 days among aspirin-allocated patients[1]

2. Where this data lives in a company

Systems of record
Electronic data capture
Owner
The trial's chief investigator and coordinating group. The data paper names its first author as Chief Investigator, responsible for the overall design, conduct and presentation of the study results.
Standards
None named by a source

This trial ran from 1991 to 1996, funded by the UK Medical Research Council, the Stroke Association and the EU BIOMED-1 programme. The data paper says baseline variables were entered and checked during a telephone call to a central randomisation service, a follow-up form was completed by the treating physician at 14 days, death or discharge, and the six-month outcome was collected by postal questionnaire or telephone interview (in Italy). For release, direct and indirect identifiers were removed, age was rounded and event dates were converted to days from randomisation. The erratum says that this anonymisation step introduced errors into thirteen date variables, later corrected. The file uses the trial's own variable names. None of the standards in this kit's registry applies to it.[2][3]

Not sourced yet: The system listed is the closest id in the kit's registry. The trial did not use an electronic data capture system as the term is used today; no opened source says which system holds the equivalent locked study database in a company.

Not sourced yet: That the analysis itself would be run in a statistical computing environment, and who owns that environment, has no opened source yet.

6. What goes wrong in practice

  • There are two versions of the file. The file published with the data paper had errors in date variables, introduced during anonymisation. The authors published an erratum and a corrected file at the Edinburgh repository. Check for an erratum before you analyse a public dataset, and record which version you used. [3][5]
  • A corrected file can change more than the erratum says. Comparing the two versions cell by cell shows thirteen changed columns. Twelve are date variables named in the erratum. The thirteenth is the month of randomisation, which the corrected file writes in another format (sty-91 where the first version has 1991-01). Compare versions yourself before you rely on a change list. Seen in this lab's data; the notebook shows it.
  • The dictionary and the file can disagree on a name. The data dictionary calls the death indicator for the whole follow-up ID. Both files call that column DIED. The first version also has two column names padded with spaces. Compare the header with the dictionary before you select columns. Seen in this lab's data; the notebook shows it.
  • A code changed during the trial. Allocated heparin has four codes. The dictionary says the higher dose was coded H in the pilot phase and M in the main trial, L is the lower dose and N means avoid heparin. Counting only M and L as heparin leaves out pilot patients. [2]
  • Analyse by allocation. The published comparison is by the treatment each patient was allocated (RXASP, RXHEP), with everyone randomised in the denominator. The file also holds what was given (DASP14) and compliance flags. Using those instead answers a different question and breaks the randomisation. [1][2]
  • Two death variables look alike. DDEAD is death recorded on the discharge form. The dictionary entry for DDEADD, the date of that death, warns that this death is not necessarily within 14 days. ID14 is the indicator of death at 14 days. Use the one that matches the outcome definition. [2]
  • Suspected stroke is not final diagnosis. Patients were randomised on a clinical diagnosis. Table 4 of the data paper shows that some had a haemorrhagic stroke or no stroke at all in the end. The published result covers everyone randomised. Restricting to the final diagnosis uses information gathered after randomisation. [2]
  • Free-text columns break the default encoding. The corrected file is not valid UTF-8 because comment columns hold other bytes. Reading it with the default settings fails. Read it as Latin-1. Seen in this lab's data; the notebook shows it.
  • Coded fields hold more than the documented codes. The diagnosis fields are documented as Y, N or U. The file also has a lower-case u and empty cells. Count the code you mean and look at the rest. Seen in this lab's data; the notebook shows it.
  • Not every printed count reproduces from the public file. The data paper's text gives the number of hospitals, of patients scanned before randomisation and of patients aged over 80. The public file gives slightly different numbers for the first two and a clearly different one for the third. Ages in the public file are rounded, which may explain the third. Report what matches and what does not; do not adjust a definition until it fits. Seen in this lab's data; the notebook shows it.

7. The same job on each platform

  • Open source executed here The lab's notebook loads the one-row-per-patient trial file (CSV) with pandas, counts deaths within 14 days by allocated aspirin arm, computes the percentages and differences, and checks them against the numbers printed by the trial's authors. This site's check runs it in a fresh Python process.[6]
  • Open source documented, not executed herepublisher-published DuckDB is a SQL database that runs inside the calling program and reads CSV files directly from disk. A learner could query the patient-level CSV file with SQL, counting 14-day deaths by allocated aspirin arm, and compare the counts with the notebook's. Not done here.[7]
  • Databricks documented, not executed herevendor-published Databricks SQL is a data warehouse that runs on the data lake and supports ANSI SQL with Delta Lake extensions, from a SQL editor, notebooks or dashboards. A learner with an account could load the trial file as a table and count deaths by arm with one query. Not done here.[8]
  • Visualisation tools documented, not executed herevendor-published Tableau Public is a free hosted platform for creating and publicly sharing data visualisations, for public, not private, data. A learner could chart the 14-day death percentages by arm there. Anything published is visible to anyone, and the data licence's attribution terms apply. Not done here.[9]
