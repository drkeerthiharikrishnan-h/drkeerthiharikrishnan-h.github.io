How common is NPM1 mutation in adult AML?

1. The question

In what share of the 200 adult de novo AML cases of the TCGA study is NPM1 mutated, and how many cases carry a mutation in each of the other genes listed in the paper's Table 1? Computed from the study's mutation file as served by the cBioPortal datahub, compared with the counts printed in the paper.

The published table counts distinct patients, not mutation records, and its denominator is a sample list, not every row in the file. Rebuilding it from the underlying mutation calls shows both counting rules and where a public file can differ from what a paper prints.

From: Table 1, "Characteristics of the 200 Patients", block "Mutation — no./total no. (%)", the twelve rows from NPM1 to KIT[1]

6. What goes wrong in practice

  • Four of the 200 listed cases have no row in the MAF. The case list (the denominator) holds 200 distinct sample ids; only 196 of them appear in the MAF file. A case with no called mutation is still a case. Dividing a gene's count by 196 instead of 200 gives the wrong percentage (NPM1 would read 27.6%, not the published 27.0%). Seen in this lab's data; the notebook shows it.
  • Count samples, not mutation rows. A gene can have more mutation rows than mutated samples. NPM1 has 55 rows in 54 samples (one sample carries two NPM1 mutations); TET2 has 27 rows in 17 samples. Count distinct Tumor_Sample_Barcode values, never rows. Seen in this lab's data; the notebook shows it.
  • The portal's re-annotation touches four rows. The cBioPortal FAQ says mutation calls go through an internal pipeline that annotates variant effects. The counts that follow are from this lab's notebook. All 2,532 rows are validated somatic calls, so none are dropped to reproduce Table 1 as printed ("Mutation" with no qualifier). But the portal's own re-annotation classes two FLT3 insertions, one TET2 insertion and one TP53 substitution (p.T125=) as Splice_Region; dropping Splice_Region rows would give FLT3 54 instead of the published 56, and TP53 15 instead of 16. [2] Seen in this lab's data; the notebook shows it.
  • Three counts do not reproduce from this file. Computed from the file, DNMT3A comes out 49 against a published 51, RUNX1 17 against 19, and IDH1-or-IDH2 38 against 39 (single-gene counts 19 and 20, one sample mutated in both). The paper's own per-patient table (Supplemental Table 01, on the GDC publication page) lists DNMT3A in 51 patients and RUNX1 in 19. So the cBioPortal file used here lacks the DNMT3A calls of two patients and one RUNX1 mutation, and one of the 19 RUNX1 entries is a gene fusion. For IDH1 or IDH2 that table gives 19 and 20 with one patient in both, so 38 patients and 39 entries; the paper prints 39, and no opened source says which of the two Table 1 counts. Why the portal's file lacks these calls is not established here; it holds 2,532 rows against the paper's own count of 2,585 validated tier-1 mutations. The checks stay as printed. [5][6][1]

7. The same job on each platform

  • Open source executed here The lab's notebook downloads the pinned MAF and the 200-case list with the Python standard library, reads them with pandas, counts distinct mutated samples per gene over the case list, and compares the counts with Table 1. This site's check runs it in a fresh Python process.[7]
  • Visualisation tools documented, not executed herepublisher-published The cBioPortal repository describes a portal, under the Apache License 2.0, for visualisation, analysis and download of large-scale cancer genomics data sets. A learner would open study laml_tcga_pub on the public portal and look at the Table 1 genes. Not done here.[8]
  • AWS documented, not executed herevendor-published The registry page lists an open S3 bucket, readable with no AWS account, holding TCGA masked somatic mutation data from the Genomic Data Commons, and a controlled bucket for raw and annotated calls. A learner could look there for the AML project's mutation files. Their presence, and any match with the file used here, is not checked.[9]
  • Open source documented, not executed herepublisher-published DuckDB is an analytical SQL database that runs inside the calling program, with no separate server, and reads CSV, Parquet, JSON and Excel files from local disk or remote endpoints. A learner could load the MAF as a text table and count distinct Tumor_Sample_Barcode values per Hugo_Symbol in SQL. Not run here.[10]
