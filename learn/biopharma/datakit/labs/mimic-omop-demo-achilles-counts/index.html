Counting patients, visits and drugs in the MIMIC-IV demo in OMOP

Load five tables of the 100-patient MIMIC-IV demo in the OMOP common data model and rebuild with SQL the counts of persons, deaths, visits and drug exposures that the project's own Achilles characterization run published.

1. The question

After the MIMIC-IV demo is mapped to the OMOP common data model, how are its patients, visits and drug exposures counted with SQL, and do the counts match the ones the project published from its Achilles run?

A common data model lets one SQL query run on many hospital databases. A count is only comparable if its definition is the same everywhere. Achilles fixes those definitions (distinct persons or records, inside an observation period, small cells removed). Rebuilding its numbers by hand shows what each definition does to real hospital records.

From: Project ZIP, folder 2_achilles_json: person.json (SUMMARY, GENDER_DATA), death.json (DEATH_BY_TYPE), visit_treemap.json (NUM_PERSONS, RECORDS_PER_PERSON), drug_treemap.json (the three drug concepts with the most persons)[1]

2. Where this data lives in a company

Systems of record
Warehouse or lakehouse, Electronic health records and claims
Owner
In this project, the authors of the PhysioNet release and the OHDSI community researchers who maintain the MIMIC to OMOP ETL on GitHub. The source hospital records come from the Beth Israel Deaconess Medical Center, through the MIMIC-IV demo.
Standards
OMOP CDM

The project page says the OMOP model represents healthcare data from diverse sources in a consistent and standardized way, and that the ETL was written in SQL wrapped in Python, using OMOP vocabulary tables to map source codes to standard concepts. It also says the authors ran the OHDSI tools Achilles and Data Quality Dashboard on the result. The two systems listed are the closest ids in the kit's registry.[2][3][4][5]

6. What goes wrong in practice

  • A count needs a definition. Achilles analysis 200 counts distinct persons with a visit of each type; analysis 201 counts visit records. Records per person is the second divided by the first. Say which one you report. [6]
  • Records outside an observation period are dropped. In the Achilles code used here (a commit inferred by this lab, not named by the project), visits, drug exposures and deaths are counted only if their start date falls inside one of the person's observation periods. A plain GROUP BY on the event table can give larger numbers. The project page says most data quality issues relate to the MIMIC date shift. [6][3]
  • Small cells are deleted, not zero. Achilles deletes any result with a count of 5 or fewer by default. In person.json the race counts add up to 87 of 100 persons. A missing row means the count was 5 or fewer, not that it was zero. [6][1]
  • The vocabulary is not in the files. The CSVs carry only the local concepts of this project (ids above 2 billion). Names of standard concepts such as 9201 Inpatient Visit come from the Achilles files here. To work with standard concepts in full, get the OMOP vocabulary by the standard route the project page describes. [3]
  • The two parts of the release have different dates. The Achilles files are dated 2021-04-26 and the OMOP CSVs 2021-05-17. A published characterization can describe an earlier build of the same tables. Check the dates before you trust a match or a mismatch. [3][1]
  • Dates are shifted. The demo page says de-identification shifted each patient's dates consistently, by a random amount. The page does not give the resulting years; in the visit_occurrence.csv of this project the visit dates run from 2110 to 2202. Durations within one patient hold; calendar years do not. [5]

7. The same job on each platform

  • Open source executed here The lab's notebook loads five OMOP tables of the MIMIC-IV demo with pandas, writes them into SQLite with Python's built-in sqlite3 module, counts persons, deaths, visits and drug exposures with SQL, and compares the counts with the project's published Achilles results in Python. This site's check runs it in a fresh Python process.[7]
  • Open source documented, not executed herepublisher-published The OMOP CDM site describes each released version of the model, its table and field conventions and the OHDSI standardised vocabularies. A learner would read the PERSON, DEATH, VISIT_OCCURRENCE and DRUG_EXPOSURE definitions there before writing the counting queries. Not done here.[8]
  • Microsoft documented, not executed herevendor-published Healthcare data solutions in Microsoft Fabric include OMOP transformations that prepare data for standardised analytics. The page says Microsoft is changing the solution's delivery model. A learner with access could hold the OMOP tables in Fabric and run the person, visit and drug-exposure counts there, after reading that notice. Not done here.[9]
  • Google Cloud documented, not executed herevendor-published BigQuery is a managed, serverless data platform for managing and analysing data with SQL and Python. A learner with a Google Cloud project could load the five OMOP CSV tables into BigQuery and run the counts with SQL, keeping the ODbL attribution. Not done here.[10]
